# Security model

What Bear Den protects, from whom, and where each control is enforced. The
surfaces, from the most exposed:

1. **The LAN**: the phone remote's HTTP/WebSocket server, off until the owner
   consents on the TV ([Controls](#controls-where-enforced): pairing, cookies,
   CSRF, Host/Origin, guest passes, app icons).
2. **Outbound traffic**, each only after the owner turns it on: Open-Meteo
   (weather), plex.tv and the owner's Plex server (Plex rows), Flathub
   (app installs and updates), the streaming sites inside Chromium.
3. **The desktop**: keys, windows, DPMS and (on Wayland) the compositor's
   window list, reached only through the coordinator's router.
4. **Local channels**: the shell/CLI IPC socket, Chromium's DevTools pipe,
   the HDMI-CEC device.
5. **What is stored**: `config.json`, `state.db` (phones, guest passes, Den
   badge counters), the keyring (Plex token), the web apps' browser profiles.
6. **What is shipped**: the `.deb` and how releases are built.

Each has a row in the table below; the longer notes for badges, installs and
web apps follow it. This model has not been through a dedicated security
review ([`VALIDATION_REPORT.md`](VALIDATION_REPORT.md#security-review)).

## Assets and trust boundaries

- **Desktop input and window control** on the TV machine: reachable only through the coordinator's action router. The phone never sends keycodes, shell strings, paths, URLs, or scripts; it sends named actions validated against [`contracts/action.schema.json`](../contracts/action.schema.json) (the list is in [`contracts/actions.md`](../contracts/actions.md)).
- **Private state** (focus, layout, device list, content rows, what is playing): visible only to authenticated devices, redacted by permission, and withheld entirely while the desktop session is locked.
- **What is playing (Now playing on phones)**: a deliberate exception to "phones never see external window titles". While an app in front exposes an MPRIS player, paired phones with the `controller` permission (or higher), and guest passes, see its title, artist or album, length, position and play/pause state (`state.now_playing`, [`contracts/http.md`](../contracts/http.md#now-playing-statenow_playing)). Anyone holding such a phone can therefore read what is on the TV. Only the foreground app's own player (matched by its adapter, as media buttons are) is read, never another player on the bus. It is omitted while the desktop is locked, for the shell, CLI peers, anonymous viewers and phones with neither `controller` nor a guest pass, and whenever the owner turns it off (TV Settings → Now playing on phones, config `remote.now_playing`, on by default). The reading lives only in the coordinator's memory: it is not written to `config.json`, SQLite, logs, diagnostics or exports, and the types that carry it print `[title]` in place of titles. `target.window_title` stays redacted for apps.
- **Secrets**: paired-device session tokens are stored as SHA-256 hashes; invitation tokens/codes are single-use with expiry and attempt limits; Plex tokens live in the Secret Service, never in `config.json`, exports, logs, or phone payloads.
- **Plex (outbound, after sign-in only)**: nothing is sent to Plex until the owner chooses Sign in in TV Settings → Plex (or runs `bear-den-tv plex sign-in`). Then the coordinator talks to plex.tv (`POST /api/v2/pins` for a link code, `GET /api/v2/pins/{id}` every 2 s until it is linked or expires, `GET /api/v2/resources` for the account's servers) and, from the moment the owner picks a server, to that server only (`/identity`, `/library/sections`, `/hubs/continueWatching` or `/library/onDeck`, `/library/sections/{id}/recentlyAdded`, `/photo/:/transcode` for posters). Rows refresh when Home comes to the front and every 10 minutes while it stays there, never while an app or another screen is in front; failures back off up to 10 minutes. The token goes into the desktop keyring (Secret Service) under `plex_content.connection_ref`, only ever travels in the `X-Plex-Token` header, and never reaches `config.json`, logs, diagnostics, the shell or phones. Without a usable keyring sign-in fails closed ("Plex sign-in needs a keyring; install or enable gnome-keyring") and nothing is sent; no file fallback exists. The link code and the sign-in flow (`state.plex`) are shown on the TV only. Phones do see the Home rows (`state.content`: titles, subtitles, progress, and poster paths on the TV they cannot fetch), like the rest of Home. Sign out deletes the token, turns `plex_content` off and deletes the cached posters. Plex HTPC keeps its own sign-in; Bear Den never touches it.
- **Location (local weather)**: off by default. Only when the owner turns weather on (TV Settings → Weather or `bear-den-tv weather set`) does the coordinator make outbound HTTPS requests (10 s timeout, `User-Agent: bear-den-tv`, no cookies or account), to Open-Meteo only (`api.open-meteo.com` for the reading every 30 minutes, `geocoding-api.open-meteo.com` for a place search the owner types). No key or account exists; the endpoints are constants in `internal/weather`, never configuration. Coordinates are rounded to 2 decimals (about 1 km) before they are stored or sent, are never logged, and never reach phones: `state.weather` is shell-only and hidden while locked. Open-Meteo sees the TV's public IP address and the rounded location, as any web service would. Nothing new listens. Settings: [`contracts/config.md`](../contracts/config.md); commands: [`docs/operations.md`](operations.md#local-weather).
- **TV control over HDMI-CEC**: off by default ([ADR 0008](decisions/0008-hdmi-cec.md)). HDMI-CEC is a slow control wire inside the HDMI cable between the box and the TV: nothing about it touches the network, and the TV stays off the network. Only when an adapter exists (`/dev/cecN`) and the owner turns it on (TV Settings → TV control over HDMI (CEC), config `cec`) does the coordinator send a fixed set of messages: Image View On, Standby (to the TV only, never broadcast), Active Source, volume keys, and Give Device Power Status. Phones send the named action `tv.power` or the existing volume actions, never CEC bytes, opcodes or device paths. Bear Den claims one playback-device address and answers only the core messages the kernel answers for it (it runs no CEC follower of its own). Opening `/dev/cecN` usually needs the `video` group; Bear Den never changes group membership or udev rules ([`operations.md`](operations.md#tv-control-over-hdmi-cec)). Any device on the same HDMI chain can also send CEC to the TV; that is HDMI's design, not something Bear Den adds.
- **Web apps (Netflix, Disney+, Hulu, the Browser tile)**: see [Web apps](#web-apps) below. Flathub Chromium, one profile per app, controlled only over a private pipe; the streaming sites are off until the owner turns them on.
- **App installs (outbound, on an owner press or the idle update only)**: see [App installs](#app-installs) below. Per user from Flathub, no root; the refs, the remote and its URL are fixed in the binary.
- **LAN listener**: off until onboarding consent; bound only to the addresses of the selected interface; loopback-only in development mode. mDNS advertisement is not wired yet, so nothing announces the TV on the network.
- **Wayland**: on wlroots compositors the coordinator is a client of `zwlr_foreign_toplevel_manager_v1` (list, activate, close, fullscreen windows) and of nothing else; it sends no input there ([ADR 0007](decisions/0007-wayland-profile.md)).
- **Packages and releases**: the `.deb` enables nothing by itself (no autostart, no service, no firewall rule). Published packages are built only by the release workflow on GitHub's runner, never on a workstation, because a local build carries the builder's home path.

## Den badges

Den badges ([`contracts/http.md`](../contracts/http.md#den-badges-stateachievements)) are the one place Bear Den counts how it is used, so they are built to say as little as possible:

- **What phones see:** badge ids, counts toward each badge (capped at its goal) and the local calendar day each badge was earned. Never a time of day, never titles or anything an app reports it is playing, never a per-day history. Only the shell and phones with `controller` get `state.achievements`; guest passes never do (the schema rejects it) and nobody does while the session is locked.
- **What is stored:** two tables in `state.db` (schema 3, [ADR 0009](decisions/0009-den-badges-local-counters.md)). `achievement_counters` holds a counter name, a count and the first and last local day it moved; `achievement_badges` holds a badge id, the day it was earned and whether Home has celebrated it. Counter names are ids such as `launches`, `launch:plex-htpc`, `app:youtube`, `days`, `night-owl`, `rain`, `season:autumn`, `theme:forest`, `guest-passes`. Their CHECKs refuse anything but lowercase ids and `YYYY-MM-DD` days, so no title, time or free text can be written, even by a bug. Nothing about what an app played ever reaches the tracker.
- **What that still says:** which apps were opened and how often (Couch Explorer, Movie Night), and on how many days Home was used, at night, in the rain. It never says when during a day, or what was on screen. Controller phones see the counts toward each badge.
- **Off switch:** config `achievements.enabled` (TV Settings → Badges → Counting, or `bear-den-tv badges off`; on by default). Off counts nothing at all; earned badges stay until **Reset badges** (or `bear-den-tv badges reset`) deletes every row. Phones can change neither ([`docs/operations.md`](operations.md#den-badges)).

## App installs

Bear Den can install the apps it knows from Flathub ([ADR 0011](decisions/0011-per-user-flathub-installs.md)):

- **Consent:** one press by the owner (the TV's Install button, Settings → Add apps, `bear-den-tv apps install`, or the owner's phone). Nothing installs on its own; opening the install card asks Flathub for the size, which is also the result of that press.
- **New outbound traffic:** to `dl.flathub.org` only (the repo file, its summary and metadata, the app's objects), only after an owner press, or for the daily update while idle when `apps.auto_update` is on (TV Settings → Keep apps up to date).
- **Fixed:** the remote (`flathub`, per user, with the URL compiled in), the ids (the adapter table's Flatpak ids only; a phone or the shell names a config app, never a ref), the architecture (x86_64) and every argv. Flatpak's own signature checks are never weakened.
- **No root:** everything runs as the TV's user with `--user`: no sudo, no polkit, no system helper; apps land in `~/.local/share/flatpak`. System-wide installs are never changed or updated ("Updated by your system"). Flatpak itself, when missing, is the owner's to install with the system package manager.

## Web apps

Netflix, Disney+, Hulu and a Browser tile run in Chromium from Flathub (`org.chromium.Chromium`), never Google Chrome ([ADR 0010](decisions/0010-web-apps-over-cdp-pipe.md)).

- **Control channel.** Bear Den starts Chromium itself with `--remote-debugging-pipe`: DevTools messages on fds 3 and 4, which only the coordinator and that Chromium hold. Nothing listens on the LAN or on loopback, there is no token to steal, and another local program or Flatpak cannot attach. If the coordinator restarts while a web app is open, that browser can no longer be driven (the phone says so) until it is closed and opened again.
- **What phones can send.** Named actions only: `nav.*`, `select`, `back`, `home`, `app.launch`, `media.*`, `text.submit` (text typed into a field the page reports focused, then Enter) and, for `controller` phones, the touchpad's `pointer.move {dx,dy}`, `pointer.click {button}` and `pointer.scroll {dy}`. Never a URL, script, selector, key code or screen coordinate. Guest passes get no touchpad; they can still use the D-pad in a web app, like any other app.
- **What Bear Den does to a page.** It injects its own navigation script (embedded in the binary) into an isolated world and performs only: clicks inside the page for OK and Back, Escape for Back, the site's documented media keys from a closed list, the phone's text, and the touchpad's pointer moves, clicks and wheel. The site sees trusted input, as from a keyboard and mouse, and cannot reach the script.
- **What leaves a page.** The script reports a role, an index and flags (text field focused, video playing or paused, visible, full screen); never labels, titles, addresses or page content. Action results carry the same. Now playing on phones may show a title if Chromium's media session reports one through MPRIS (the same rules as other apps).
- **Profiles.** Each web app has its own Chromium profile in `$XDG_DATA_HOME/bear-den-tv/web/<app-id>` (mode 0700): cookies and sign-ins stay there, separate from each other and from any personal browser. Bear Den never reads them, exports them or sends them anywhere; deleting the folder signs that app out.
- **Page addresses** are owner configuration on the TV (`config.json` `applications[].web.url`, rule 11 in [`contracts/config.md`](../contracts/config.md)), checked when loaded and again before every launch. The Browser opens `about:blank` unless the owner sets a start page; no search engine is added.
- **What the services see.** An ordinary Chromium on Linux, signed in by the owner. Bear Den adds nothing to the requests.
- **Widevine** (needed for the streaming services) comes, if at all, from Chromium's own component updater into each profile; Bear Den never downloads or copies it.
